# bilibili-fav-restore

在 bilibili 网页版收藏夹页面，自动还原失效（已删除 / UP 自删）视频的原始封面、标题与作者信息。

bilibili 网页版的收藏夹接口对失效条目仅返回固定占位封面与「已失效视频」文字。本脚本以 bilibili 自家 Android 客户端使用的接口（含正确签名）取回失效前的快照，并替换页面 DOM。对于服务端层面已被静默丢弃的条目，脚本会在页面顶端列出对应的 av 号及第三方归档站快照链接。

## 功能

- 还原失效条目的封面、标题、作者、播放数与弹幕数等元数据，并为已还原的卡片添加视觉标记（标题加删除线、卡片灰化）
- 页内悬浮按钮：可拖动定位，点击展开二级菜单，涵盖脚本的全部命令
- 检测并展示 bilibili 服务端静默丢弃的条目，提供 biliplus、xbeibeix、jijidown 三个第三方归档站的快照链接
- 在收藏夹卡片的三点菜单中注入复制、还原与重试相关的操作
- 提供 TV 端二维码登录与手动粘贴 `access_key` 两种登录模式
- 元数据本地缓存（GM storage），减少对 bilibili API 的重复请求
- 对确已删除、反复重试仍无结果的条目，支持逐条或整页停止重试；后台放弃时亦自动记录，避免每次进入收藏夹重跑同一轮采样
- 手动备份当前收藏夹（元数据与封面图本体 → IndexedDB），条目失效后直接以本地数据还原，不依赖 bilibili 或第三方归档站是否仍保有该条目；备份可导出为 ZIP 文件自行保管

## 安装

1. 安装 [Tampermonkey](https://www.tampermonkey.net/)（Chrome、Edge、Firefox 均可）。
2. 选择以下任一入口，浏览器访问后 Tampermonkey 将弹出安装对话框：

   - **[从 Greasy Fork 安装](https://greasyfork.org/zh-TW/scripts/578965-bilibili-收藏夹失效视频还原)**（推荐）
   - **[从 GitHub Raw 安装](https://raw.githubusercontent.com/k0504/bilibili-fav-restore/main/dist/bilibili-fav-restore.user.js)**

   两个入口分发同一份脚本。Greasy Fork 通过 sync 机制定期从 GitHub Raw URL 拉取新版本，延迟约 24 小时。

3. 安装完成后，Tampermonkey 会定期向所选入口检查更新，新版本将自动提示安装。

## 首次登录

1. 打开任意收藏夹页面，例如 `https://space.bilibili.com/{UID}/favlist?fid={收藏夹 ID}`。
2. 在页内悬浮按钮的菜单中选择 **账号与登录 → 登录（TV 端二维码）**。
3. 使用 bilibili 手机客户端扫描页面上显示的二维码并确认登录。**仅 bilibili 官方客户端可用**，微信扫码或网页扫码无效。
4. 登录成功后 `access_key` 会写入 GM storage，有效期约 30 天。刷新页面后，失效条目应自动恢复。

如某些条目在 TV 模式下仍无法取回原始元数据，可改用 **账号与登录 → 登录（手动输入凭据）**，粘贴一份由 Android 主端应用签发的 `access_key`（需自行通过 mitm 工具抓取）。

未配置 `access_key`（未登录或已执行注销）时，脚本不再发起任何还原相关的网络请求，仅以本地缓存与备份还原可覆盖的条目。

## 操作入口

脚本的命令有三处入口，功能等价，按使用场景选择即可。

### 页内悬浮按钮

收藏夹页面右下角常驻一枚圆形按钮，为脚本的主要入口。

- **拖动定位**：按住按钮并移动即可拖动，位移小于 4 像素时视为点击而非拖动。位置持久保存，并在窗口尺寸变化时重新约束至可视区域内，不会滞留于画面之外。如需恢复默认位置，在 DevTools Console 中执行 `__biliFavFix.fab.resetPosition()`。
- **展开菜单**：点击按钮展开一级菜单，其中为五个功能分类；点击任一分类进入二级菜单，其最上方一行为「返回」，回到一级菜单。按 Esc 键逐级返回，于一级菜单按 Esc 则关闭菜单；点击菜单以外的区域亦关闭菜单。菜单的展开方向依按钮当前所处象限自动翻转，不会开出画面之外。
- **状态提示**：一级菜单的分类与二级菜单的部分条目在右侧以浅色小字显示当前状态（登录模式、调试日志开关、停止重试记录条数、本页可停止的条目数）。该数值于菜单展开时即时计算。

菜单结构如下。其中标记为「破坏性」的两项以红色显示，其效果无法通过再次点击撤销。

| 分类 | 条目 | 说明 |
| ---- | ---- | ---- |
| 账号与登录 | 登录（TV 端二维码） | 显示二维码，以 bilibili 官方客户端扫码登录 |
| | 登录（手动输入凭据） | 粘贴自行抓取的 `access_key` |
| | 查看登录状态 | 以 toast 显示登录模式、凭据是否已保存及其保存天数 |
| | 注销（清除登录凭据）（破坏性） | 清除已保存的 `access_key` |
| 扫描与修复 | 立即重新扫描并修复 | 清除内存缓存并立即重跑一轮还原 |
| | 扫描静默丢弃的条目 | 重置相关缓存后重新检测服务端静默丢弃的条目 |
| 重试控制 | 本页全部停止重试 | 停止当前页面上全部仍在重试的条目，详见「停止重试」一节 |
| | 清除所有「停止重试」标记 | 清空全部停止记录，范围为所有收藏夹 |
| 备份 | 备份当前收藏夹 | 将当前收藏夹的元数据与封面图写入 IndexedDB |
| | 管理备份 | 打开备份管理面板，浏览、导出或删除已存备份 |
| | 导入备份文件 | 选取本机 ZIP 文件，将其中的条目合并写入 IndexedDB |
| 维护与调试 | 开关调试日志 | 切换 `debug` 日志，默认关闭 |
| | 清除所有缓存并刷新页面（破坏性） | 清除全部还原缓存并重新加载页面；不影响备份数据与停止重试记录 |

### Tampermonkey 扩展菜单

点击浏览器工具栏的 Tampermonkey 图标，可见前缀为 `fav-fix：` 的同一组命令，与悬浮按钮菜单一一对应，仅呈现为扁平列表。两处入口调用同一份实现，行为完全一致。

### 卡片三点菜单

在收藏夹卡片右上角的三点菜单中，脚本注入以下条目。部分条目按卡片当前状态互斥显示。

| 条目 | 出现条件 |
| ---- | ---- |
| 恢复重试 | 该条目已被手动停止重试。此时不再提供「立即重试」，避免为同一个已作出的决定并列两个按钮 |
| 立即重试 | 条目仍待还原（`_pending`）。以整个收藏夹的遗留集合重新驱动一轮后台采样，而非只重试所点的一条 |
| 停止重试 | 条目仍待还原（`_pending`），或标题已还原、仅封面仍在后台补取（`_cover_pending`）。后者不显示封面按钮，菜单是其唯一入口 |
| 复制 AV 号 / 复制 BV 号 | 已取得对应的 av 号 / BV 号 |
| 复制完整信息 | 始终 |
| 查看原始封面 | 已取得非占位的 http(s) 封面地址 |
| 在 biliplus 查看 | 已取得 av 号 |
| 清缓存并重抓 | 条目已还原或已判定不可还原，且未被手动停止重试。待还原的条目不显示此项，「立即重试」是其对应操作 |

### DevTools 控制台

全部功能亦可在 DevTools Console 中经 `__biliFavFix` 调用，接口列表见「开发 → 调试接口」。

## 停止重试

bilibili 的 Android 端收藏接口并不稳定，同一收藏夹的失效条目在每次遍历中会随机遗漏一部分。脚本据此对未能立即还原的条目启动后台重复采样：连续七轮无新增即判定为无法取回并停止，全程约四分钟。对于确实已被永久删除的条目，该过程不会有任何结果，却会在每次进入该收藏夹时重新执行一遍。

为此脚本提供两层抑制机制，二者共用同一份记录，每个条目至多一条：

| 类型 | 写入时机 | 有效期 |
| ---- | ---- | ---- |
| 手动停止 | 使用者显式停止 | 永久，直至显式恢复 |
| 自动记录 | 后台采样确实放弃时自动写入 | 7 天，到期后该条目恢复正常重试 |

手动停止优先于自动记录：已手动停止的条目不会被自动记录覆盖，自动记录亦不会削弱手动停止的永久性。后台采样因切换收藏夹而中断时不写入自动记录，中断不等同于结论。

### 逐条操作

- **封面按钮**：处于「重试中」或「待重试」状态的卡片，其封面正中央有一枚常驻圆形按钮，按当前状态显示停止图标（方块）或恢复图标（循环箭头），点击即执行；指针悬停时由原生提示显示「停止重试」或「恢复重试」。封面左上角的小标签仅指示状态，不可点击。
- **卡片三点菜单**：提供「停止重试」与「恢复重试」两项，按卡片当前状态互斥显示。标题已还原、仅封面仍在后台补取的条目不显示封面按钮，菜单是其唯一入口。

### 整页与全局操作

- **本页全部停止重试**（菜单 → 重试控制）：作用对象为当前页面上仍在重试的条目，即画面中处于「重试中」或「待重试」的卡片，与后台采样在本收藏夹放弃的条目集合之并集，已停止者除外。菜单中该项右侧显示的数量即为本次点击将影响的条目数。执行后当前页面立即重绘，无需刷新。
- **清除所有「停止重试」标记**（菜单 → 重试控制）：清空全部停止记录，手动与自动一并清除。停止记录以 av 号为键，不区分收藏夹，因此该操作的范围是**所有收藏夹**，而非当前页面。脚本将报告清除的手动与自动记录条数并重绘当前页面，无需刷新。

### 语义边界

停止的对象是网络重试，不影响本地数据：已手动备份的条目仍会照常以本地备份还原，停止记录亦不受「清除所有缓存」影响。恢复重试将一并清除该条目的还原缓存并立即重新抓取一轮。

## 备份至 IndexedDB

前述还原流程属于事后补救：条目失效之后，脚本才向 bilibili Android 端接口与第三方归档站索取残留快照，能否取回不由脚本决定。备份功能与之相反，用于在条目仍然有效时预先留存。

### 执行备份

在收藏夹页面选择 **菜单 → 备份 → 备份当前收藏夹**，脚本将逐页遍历当前收藏夹，把标题、简介、UP 主、分区、时长、投稿与收藏时间等元数据，以及封面图的图片本体，写入浏览器的 IndexedDB 数据库 `bili-fav-fix-backup`。执行过程中会以页为单位显示进度，结束时汇总新增、更新、跳过与封面下载失败的条目数。

该收藏夹中的条目日后失效时，备份将作为优先级最高的数据源参与还原流程：封面与元数据直接取自本地，不依赖 bilibili 或第三方归档站是否仍保有该条目。即使 bilibili CDN 已清除封面图文件，脚本也会改用备份中的图片本体填充卡片封面。

需要说明的是，在已登录的情况下，脚本首次处理某个收藏夹页面时仍会照常遍历收藏夹接口，以确定各条目的当前状态与跳转目标，备份并不取消该步骤。

补充说明：

- 备份可重复执行。封面地址未发生变化的条目仅更新元数据，不会重复下载图片，因此对同一收藏夹再次备份的开销远低于首次。
- 重复备份不会覆盖已有的封面图片。若某条目在本次备份时已经失效，或其封面地址已变更而新地址下载失败，脚本将保留此前存入的图片本体，并在结果汇总中以「沿用旧封面」计数。
- 备份时已失效的条目，若此前曾被还原并写入缓存，将以该还原结果入库；否则计入「跳过失效」，不写入占位封面与「已失效视频」标题。
- 备份状态整合于备份管理面板：面板顶部显示已备份条目总数、封面占用体积与浏览器存储用量；在收藏夹过滤中选定某一收藏夹时，底部同时显示该收藏夹最近一次完整备份的时间。若上一次执行中途失败，会另行标注中止页码，此前完整备份的记录不会被覆盖。
- 任何清除缓存的操作均不会删除备份数据。删除备份需经由备份管理面板显式执行。

### 管理备份

选择 **菜单 → 备份 → 管理备份**，将在页面内打开备份管理面板，用于浏览、导出与删除 IndexedDB 中已存的备份条目。

面板功能：

- 列表默认按收藏时间倒序排列（与收藏夹页面的「最近收藏」顺序一致），可通过排序下拉在收藏时间与备份时间的升降序之间切换；每页 20 条，逐条显示封面缩略图、标题、UP 主、收藏或备份日期（随排序依据切换）、封面体积，以及数据来源标签（「备份时有效」表示备份时条目仍然有效，「取自还原缓存」表示备份时条目已失效、内容取自此前的还原结果）。
- 顶部显示已备份条目总数、含封面条目数、封面占用体积与浏览器存储用量；选定某一收藏夹时，底部页码栏同时显示该收藏夹最近一次完整备份的时间与可能的中止标注。
- 工具栏提供关键词搜索（匹配标题、BV 号与 UP 主名称）与收藏夹过滤。过滤选项为各条目所属收藏夹的并集，以收藏夹名称显示并标注当前收藏夹；仅已执行过备份的收藏夹会出现在选项中。
- 工具栏的「备份当前收藏夹」按钮与菜单中的同名命令等效，以页面当前所在的收藏夹为备份对象。欲备份尚未出现在过滤选项中的收藏夹，先在页面左侧切换至该收藏夹，再点击此按钮；备份完成后面板自动刷新，该收藏夹随即可供过滤。备份进行期间删除操作暂不可用，浏览不受影响。
- 底部的「导出筛选结果」按钮将当前筛选结果打包为 ZIP 文件并交由浏览器下载，详见「导出为 ZIP 文件」一节。该操作为只读，不修改亦不删除任何备份数据，因此不设二次确认。
- 底部与「导出筛选结果」并列的「导入备份文件」按钮，点击后打开文件选择对话框，用于选取待导入的 ZIP 文件；格式要求、校验规则与合并语义详见「从 ZIP 文件导入」一节。
- 单条删除需二次确认；「删除当前筛选结果」按当前搜索与过滤条件批量删除，筛选条件为「全部收藏夹」且搜索框为空时即为清空全部备份，确认提示会明确标示该情形。
- 删除操作不可撤销。删除某条目时，脚本会一并清除该条目由备份数据生成的还原缓存，避免删除后卡片仍以备份内容还原。

面板亦可在 DevTools Console 中以 `__biliFavFix.backup.manage()` 打开。关闭方式为右上角「关闭」按钮、点击面板外的遮罩区域或按 Esc 键。

### 导出为 ZIP 文件

备份数据存放于浏览器的 IndexedDB，受同源策略约束，且在存储压力下可能被浏览器回收。导出功能用于将其取出为可自行保管的文件。

在备份管理面板中设定搜索与收藏夹过滤条件后，点击底部的「导出筛选结果」，脚本将按当前排序遍历筛选结果，打包为一个 ZIP 文件并触发下载。文件名格式为 `bili-fav-backup_<范围>_<日期-时间>.zip`：选定单一收藏夹时，范围取该收藏夹名称，否则为「全部」；搜索框非空时另附「_筛选」。

压缩包采用 STORE 方式存储（不作压缩，封面图片本身已为压缩格式），内部结构如下：

| 路径 | 内容 |
| ---- | ---- |
| `manifest.json` | 格式自描述：格式标识与版本、导出时间、来源域名、核心版本、本次导出的筛选范围、条目与封面统计，以及所涉各收藏夹最近一次完整备份的记录摘要。 |
| `items.json` | 全部条目的元数据数组，顺序与导出时的面板排序一致。每条包含 IndexedDB 记录中除封面图片本体以外的全部字段，并附 `cover_file` 指向压缩包内对应的封面文件；条目无封面或封面读取失败时该字段为 `null`。 |
| `covers/<av>.<ext>` | 封面图片的原始字节。扩展名由记录中的 MIME 类型推导（`jpg` / `png` / `webp` / `gif`），类型未知时为 `bin`。 |

补充说明：

- 导出内容为点击瞬间的筛选结果快照。导出期间修改搜索、过滤或排序条件均不影响本次导出结果。
- 导出期间按钮原地显示进度百分比，删除操作暂不可用，浏览与翻页不受影响；反之，备份执行期间不可导出，以免导出到一份新旧混杂的数据。
- 受 ZIP 格式 32 位字段限制（未采用 ZIP64），预计体积超过 3.5 GiB 或条目数接近 65000 时将拒绝执行并提示按收藏夹分批导出。
- 若某条目的记录在建立列表之后已被删除，或其封面图片本体无法读取，该条目分别计入「记录缺失」与「封面读取失败」，并在完成提示中标出；其余条目照常导出。
- 亦可在 DevTools Console 中执行 `__biliFavFix.backup.exportAll()`，不经面板直接导出全部备份条目。

### 从 ZIP 文件导入

三处入口均会打开文件选择对话框，用于选取待导入的 ZIP 文件：**管理备份面板**底部与「导出筛选结果」并列的「导入备份文件」按钮、悬浮按钮菜单 **备份 → 导入备份文件**，以及 Tampermonkey 扩展菜单中的同名命令 `fav-fix：导入备份文件`。三处入口调用同一份实现。

**格式接受范围**：导入接受本脚本导出的 ZIP 文件（`manifest.json` + `items.json` + `covers/`），也接受将该内容解压后以任意 DEFLATE 压缩工具重新打包的压缩包，内部结构与文件名不变即可。不支持加密压缩包，亦不支持 ZIP64（超过 4 GiB 或 65535 个成员的压缩包）。

**校验与拒绝**：导入前逐一校验压缩包内每个成员的 CRC。核心文件（`manifest.json` 或 `items.json`）校验失败时，整个导入被拒绝；单个封面图片校验失败时，仅跳过该封面，其对应条目的元数据仍照常导入。脚本亦会拒绝并非本脚本格式的压缩包，以及 `manifest.json` 中 `format_version` 高于当前脚本版本的压缩包，后者会提示先升级脚本再重试。

**合并语义**：导入以 av 号为键，与 IndexedDB 中的既有记录逐条合并：

- 记录本体以 `backed_at`（备份时间）较新的一侧为准。
- `media_ids`（所属收藏夹集合）不论合并方向，一律取并集，不会丢失任一侧的收藏夹归属。
- 封面图片本体不会被空值覆盖：只要任一侧存有封面字节，合并结果即保留该封面。
- 因此重复导入同一份文件是幂等操作，全部条目计入「保留」，不会产生重复写入。

**跨域迁移**：`manifest.json` 中的 `origin` 字段仅供参考信息，不作为导入的限制条件。在 `space.bilibili.com` 导出的 ZIP 文件可原样导入到 `www.bilibili.com`，反之亦然——这是在两个独立 IndexedDB 数据库之间迁移备份数据的支持方式。

**互斥限制**：导入与「备份当前收藏夹」及「导出筛选结果」互斥，三者之一进行期间，发起其余操作将被拒绝并以 toast 提示。

导入结束后以 toast 汇总新增、更新与保留的条目数，以及封面的对应计数与跳过或损坏的成员数。

## 已知限制

- 仅支持本人收藏夹或公开收藏夹。私密收藏夹受 API 鉴权限制无法读取。
- 脚本返回的「原始封面」托管于 bilibili CDN。若 bilibili 在服务端清除该资源文件，脚本无法恢复，此前已执行手动备份的条目除外。
- 每页 20 条，最多翻阅 50 页（约 1000 条）。如需调整，修改 `src/01-constants.js` 中的 `MAX_PAGE_WALK`。
- 若 API 返回 `-3` / `-101` / `-663`，通常表示 appkey 或 appsec 已被 bilibili 更新，需重新抓取并替换 `src/01-constants.js` 中的 appkey / appsec 常量。
- 第三方归档源（biliplus、xbeibeix、jijidown）的可用性与命中率不在脚本控制范围内。
- 「停止重试」记录不在多个标签页之间实时同步。脚本未申请 `GM_addValueChangeListener` 权限（bootstrap 的 `@version` 已永久锁定，无法追加权限声明），因此在某一标签页停止或恢复某条目后，其他已打开的收藏夹标签页需刷新后才会反映该变更。
- 悬浮按钮的位置同样保存于 GM storage，且不随标签页实时同步；在一处拖动后，其他已打开的标签页需刷新才会采用新位置。
- 备份数据库受浏览器同源策略约束，`space.bilibili.com` 与 `www.bilibili.com` 各自持有独立的一份。在其中一个域名下备份的数据，在另一个域名下无法读取，需分别备份。备份亦不随浏览器配置文件同步，更换浏览器或清除站点数据后不再存在；如需长期保管，请使用备份管理面板的导出功能。

## 开发

仓库同时维护两套 Tampermonkey 入口，分别面向端用户与开发者。

| 文件 | 用途 |
| ---- | ---- |
| `dist/bilibili-fav-restore.user.js` | 端用户安装文件。由 `build.py` 从核心代码生成，提交后通过 GitHub raw URL 对外分发。 |
| `bilibili-fav-list-fix.user.js` | 开发用 bootstrap，`@version` 永久锁定为 `1.0.0`。仅负责从本地 HTTP 服务拉取核心代码并执行，避免每次修改核心都需重新安装 Tampermonkey。 |
| `src/*.js` | 核心代码，按关注点拆分为多个模块（签名、DOM 替换、菜单注入、登录流程、静默丢弃检测等）。两套入口共享同一份核心。各模块职责详见 `AGENTS.md` 的「src/ 模块地图」。 |
| `bundle.py` | 核心代码组装的单一来源。`MANIFEST` 定义模块加载顺序，将 `src/*.js` 拼接还原为单一 IIFE；`serve.py` 与 `build.py` 共享此函数，保证开发与发布产物一致。 |
| `serve.py` | 本地 HTTP 服务（默认 `127.0.0.1:8766`）。响应 bootstrap 请求时即时调用 `bundle.py` 组装核心代码（磁盘上无单文件核心），端用户无需运行。 |
| `build.py` | 将核心代码（经 `bundle.py` 组装）打包为 `dist/bilibili-fav-restore.user.js`，并自动从中提取 `CORE_VERSION` 写入 `@version`。 |

### 开发循环

```bash
python serve.py
# 浏览器地址栏访问 http://127.0.0.1:8766/bilibili-fav-list-fix.user.js
# Tampermonkey 弹出安装对话框，确认安装 bootstrap（仅需一次）
```

随后编辑 `src/` 下的任一模块，刷新任意收藏夹页面即可生效（`serve.py` 每次请求都会重新组装核心代码，无需构建步骤）。bootstrap 每次都会附加 cache-bust 参数，无需手动清除缓存。

新增 `src/` 模块时须同步在 `bundle.py` 的 `MANIFEST` 中登记，并重启 `serve.py`：该模块在导入时读取 `MANIFEST`，运行中的进程不会感知新增条目。

### 发布

1. 修改 `src/00-prologue.js` 中的 `CORE_VERSION`。Tampermonkey 仅在版本号增大时触发自动更新。
2. 运行 `python build.py` 重新生成 `dist/bilibili-fav-restore.user.js`。
3. 提交 `src/` 与 `dist/` 目录并推送到 GitHub。Tampermonkey 通常在 24 小时内为端用户拉取新版本。

### bootstrap 安装注意事项

- 必须在浏览器地址栏直接访问 `http://127.0.0.1:8766/bilibili-fav-list-fix.user.js`。Tampermonkey 官网的 `script_installation.php?url=...` 中转页对本地 HTTP 资源不会重定向。
- 本地服务返回的 `Content-Type` 必须为 `application/javascript`，`serve.py` 已强制此值。
- 在 Tampermonkey Dashboard 中将 **Settings → Config mode** 切换为 `Advanced`，并在 **Security → Allow scripts to access cross-origin resources** 中勾选允许。

### 为何不使用 Tampermonkey 的 `@updateURL` 自动更新

Tampermonkey 拒绝 `http://127.0.0.1` 作为 `@updateURL`（insecure-origin policy）。dev 用 bootstrap 的存在即为解决此限制：bootstrap 自身锁定版本永不更新，核心逻辑则由本地 HTTP 服务每次重新拉取。端用户安装的 `dist/` 文件通过 GitHub raw URL 分发，不受此限制影响。
